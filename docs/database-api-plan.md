# DB 구성 및 API 전환 계획

> 계획 문서입니다. 현재 앱은 단일 사용자 로컬 데모이며, 아래 DB·인증·루틴 API는 아직 구현되지 않았습니다.

## 목표와 범위

브라우저의 `morrow-v1` 데이터(루틴, 기록, 진행 중 타이머)를 계정별 서버 데이터로 옮겨 기기 간에 사용할 수 있게 한다. 기존 목표 시간은 **주간 분**, 기록 시간은 **초**로 유지한다. 기존 월요일~일요일 주간 계산과 날짜별 누적 표시를 보존한다. 영상 원본과 결과물은 DB에 저장하지 않는다.

## 구성안

- Next.js App Router의 Route Handler를 API 계층으로 사용하고, 서비스 계층에서 검증과 업무 규칙을 처리한다. 클라이언트가 DB에 직접 접근하지 않는다.
- PostgreSQL을 기준 DB로 한다. 로컬 개발은 별도 개발 DB를 사용하고, 운영 DB와 자격 증명을 분리한다. DB 접근 라이브러리와 호스팅은 구현 시 마이그레이션·트랜잭션·운영 환경을 검토해 확정한다.
- 인증은 검증된 인증 제공자를 도입하고 서버 세션에서 사용자 ID를 얻는다. 제공자는 배포 환경과 로그인 방식을 결정할 때 확정한다. 모든 개인 데이터 쿼리는 서버 측 사용자 ID로 범위를 제한한다.
- 비밀값은 환경 변수로 관리하고 저장소에 커밋하지 않는다. 개발·테스트·운영 환경의 DB와 인증 설정을 분리한다. 스키마 변경은 버전 관리된 마이그레이션으로 적용하고 운영 적용 전 백업과 복구를 검증한다.

## 데이터 모델 초안

모든 ID는 서버 발급 UUID, 시각은 UTC `timestamptz`를 사용한다. 날짜는 사용자의 달력 날짜를 표현하는 `date`이며 사용자 시간대를 별도로 보관한다.

| 테이블 | 주요 필드 및 제약 |
| --- | --- |
| `users` | `id`, 인증 제공자 식별자(유일), `timezone`(IANA, 기본 `Asia/Seoul`), `created_at`, `updated_at` |
| `routines` | `id`, `user_id` FK, `name`, `weekly_goal_minutes` 양수, `icon`, `color`, `created_at`, `updated_at`, `archived_at` nullable |
| `routine_logs` | `id`, `user_id` FK, `routine_id` FK, `routine_name_snapshot`, `seconds` 양수, `record_date` date, `mode` (`manual`/`timer`), `created_at`, `updated_at` |
| `active_timers` | `user_id` 유일 FK, `routine_id` FK, `elapsed_seconds` 0 이상, `started_at` nullable, `version`, `updated_at` |
| `import_batches` | `id`, `user_id` FK, `client_import_id`, `created_at`; `(user_id, client_import_id)` 유일로 재시도 중복 방지 |

루틴 삭제는 보관 처리로 기록을 보존하고, 기록의 이름 스냅샷으로 당시 표시명을 유지한다. 기록·타이머의 루틴은 반드시 같은 사용자 소유여야 한다(복합 FK 또는 트랜잭션 내 소유권 검사). `routine_logs(user_id, record_date)`와 `routine_logs(user_id, routine_id, record_date)` 인덱스로 날짜·주간 조회를 지원한다. 주간 목표 변경 시 과거 기록에 현재 목표를 적용하는 기존 동작을 우선 유지한다.

## API 초안

모든 경로는 `/api` 아래, JSON UTF-8을 사용한다. 인증되지 않은 요청은 401, 다른 사용자 소유 또는 없는 리소스는 404로 처리한다. 입력 오류는 400 또는 422, 충돌은 409, 제한 초과는 429, 서버 오류는 500을 사용한다. 오류는 `{ "error": { "code": "...", "message": "..." } }` 형태로 반환하고 내부 오류를 노출하지 않는다. 상태 변경 요청은 세션 쿠키 사용 시 CSRF 방어를 적용한다.

| 메서드·경로 | 역할 |
| --- | --- |
| `GET /api/routines` | 활성 루틴 조회 |
| `POST /api/routines` | 이름, 주간 목표 분, 아이콘, 색상 검증 후 생성 |
| `PATCH /api/routines/:id` | 소유 루틴 수정 |
| `DELETE /api/routines/:id` | 루틴 보관 처리. 기록은 보존 |
| `GET /api/logs?from=YYYY-MM-DD&to=YYYY-MM-DD` | 소유 기록 기간 조회. 범위 상한과 페이지네이션 적용 |
| `POST /api/logs` | 수기 기록 생성. 루틴 소유권, 날짜, 초 단위 시간 검증 |
| `DELETE /api/logs/:id` | 소유 기록 삭제 |
| `GET /api/timer` | 진행·일시정지 중인 타이머 조회 |
| `POST /api/timer/start` | 단일 활성 타이머 시작. 이미 존재하면 409 |
| `POST /api/timer/pause`, `POST /api/timer/resume` | 서버 시각을 기준으로 경과 시간 갱신; 상태·버전 충돌 시 409 |
| `POST /api/timer/finish` | 경과 시간을 기록으로 저장하고 타이머 제거. 하나의 트랜잭션 및 멱등 키로 재시도 중복 방지 |
| `POST /api/import/local` | 확인된 로컬 데이터 일괄 가져오기. 배치 ID로 중복 방지하고 전체 트랜잭션 적용 |
| `POST /api/export` | 기존 multipart 영상 내보내기 유지. 운영 전 아래 제한 보완 |

날짜별·주간 통계는 우선 기간별 기록과 루틴을 기준으로 계산한다. 서버 전환 시 사용자 시간대의 월요일 00:00부터 일요일까지를 기준으로 기존 계산과 동일한 결과를 테스트한다. 기록 날짜는 타이머 종료 시 사용자 시간대의 날짜로 확정하며, 수기 기록은 선택한 날짜를 사용한다. 시간대 변경 및 자정을 넘긴 타이머의 정책은 구현 전에 사용자 경험을 확인한다.

## 영상 API 운영 전 보완

현재 `/api/export`는 요청 본문을 메모리에 읽고, 프로세스 내부 `busy` 변수로 동시성을 제한하며, 임시 폴더를 `finally`에서 정리한다. 이 제한은 다중 프로세스·서버 인스턴스 간 공유되지 않고 강제 종료 시 정리가 보장되지 않는다.

운영 전 인증과 사용자별 제한, 실제 스트리밍 크기 제한(헤더만 신뢰하지 않음), 파일·컷 검증, 공유 작업 큐와 동시성 제한, 작업 시간 제한 및 실패 복구를 적용한다. 임시 파일은 작업별 격리하고 완료·실패·강제 종료 후 TTL 청소를 구현한다. 파일을 외부 임시 저장소로 옮기는 경우 접근 제한과 삭제 정책을 마련하고, 결과 다운로드 후 원본과 결과물을 지운다. 영상은 영구 보관하지 않는다. 현재 즉시 응답 방식에서 비동기 작업 방식으로 바뀌면 작업 상태·다운로드 API를 별도 설계한다.

## 기존 데이터 이관

1. 로그인 후 `morrow-v1` 존재 여부를 확인하고 사용자에게 가져오기 여부를 묻는다. 자동으로 기존 데이터를 덮어쓰지 않는다.
2. 로컬 JSON을 검증하고 기본 루틴 ID 및 루틴 참조를 새 UUID로 매핑한다. 이름 스냅샷과 날짜, 초, 모드를 보존한다. 고아 기록·잘못된 데이터는 표시하고 사용자가 수정하거나 제외하도록 한다.
3. 활성 타이머는 실행 중/일시정지 상태와 경과 시간을 보존하도록 가져오기 시점의 타임스탬프를 검증한다. 충돌 중인 서버 타이머가 있으면 자동 병합하지 않고 선택을 요청한다.
4. 가져오기는 사용자별 배치 ID를 사용해 트랜잭션으로 처리하고 재시도해도 중복되지 않게 한다. 성공 검증 전 로컬 데이터를 삭제하지 않는다. 완료 후에도 사용자가 확인할 때까지 백업을 유지한다.

## 구현 순서와 완료 기준

1. DB·인증 제공자와 배포 환경 확정, 개발/테스트 DB 및 마이그레이션 구성.
2. 인증과 소유권 검사, 루틴·기록 API 및 DB 제약 구현. 다른 사용자 접근, 유효성 오류, 삭제 후 기록 보존을 테스트.
3. 단일 타이머의 동시 요청·재시도·자정 경계 및 트랜잭션 테스트.
4. 로컬 데이터 가져오기와 충돌 처리 구현. 실패·재시도에도 원본 보존 및 중복 없는지 검증.
5. 프런트엔드를 API로 전환하고 주간 집계·날짜·시간대 회귀 테스트. 로컬 데모에서 클라우드 모드 전환에 따른 실패 상태를 명확히 표시.
6. 영상 API 운영 제한과 정리 작업을 보완하고, 백업·복구·관측·배포 환경을 검증한다. `develop`에서 테스트 후 PR로 `main`에 반영한다.
